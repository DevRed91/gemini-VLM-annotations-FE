# Chat Object Search — Phase 3 Viewer Selection API

**Status: implemented and validated.**

Phase 3 connects local search results to the existing annotation visuals in the real Gaussian Splat viewer. Selection is keyed by canonical annotation IDs (`annotation-N`), never Gaussian indices, and does not refit OBBs, rerun DBSCAN, invoke `clusterLifter`, or alter Gaussian data.

## Architecture and ownership decisions

| Concern | Owner |
|---|---|
| Annotation existence and geometry | `SplatViewer` `ViewerAnnotation` collection, `SpatialObjectRegistry`, and existing annotation creation/removal lifecycle |
| Chat selection state | `SplatViewer`, backed by the small dependency-free `ChatAnnotationSelection` state core |
| Annotation pin/label/card interaction | Existing `createAnnotationElement()` handlers; card opening/closing remains independent |
| Chat parsing/search/result rendering | `ChatController` and `ChatPanel` |
| Optional Gaussian highlighting | Existing `GaussianObjectHighlighter`; chat selection neither creates nor clears it |

The public viewer API is:

```ts
viewer.setChatSelection(annotationIds: readonly string[]): void;
viewer.clearChatSelection(): void;
viewer.getChatSelection(): string[];
```

`setChatSelection` resolves input against the current `ViewerAnnotation[]` collection. Stale/missing IDs and duplicates are ignored, while a malformed non-array argument throws a controlled `TypeError`. Selection updates are synchronous and proportional to annotation count, not splat count. Chat code communicates IDs only and never touches annotation DOM or Three.js objects.

## Selection behavior

- Each chat result has a **Select in scene** action and selects only that valid annotation.
- Each result group has **Select all in scene** and **Clear selection** actions.
- A new submitted query explicitly clears the previous chat selection; results are never selected automatically.
- Clearing the conversation also clears the chat selection.
- Annotation deletion, clear-all annotations, and world reload remove/clear the chat selection through the existing annotation lifecycle.
- Existing annotation card toggling, manual deletion, and optional Gaussian ownership remain independent. Clear-all necessarily removes all annotations and therefore also removes their chat selections.
- `loadWorld()` uses the existing `worldGeneration` guard for asynchronous loading/annotation work. Selection itself is cleared synchronously before old resources are removed, so old IDs cannot affect a new world.

## Visual treatment

The selected treatment is one consistent state, `.annotation-container--chat-selected`:

- Stronger pin color, scale, border, and glow.
- Distinct label border and glow.
- Distinct card border and glow when a card is open.
- Cluster OBB wireframes use the accent color `#38bdf8`; clearing selection restores the helper's original stored color.
- Pin-only annotations receive the same pin/label/card treatment and do not require an OBB.

No annotation position, OBB, helper geometry, Gaussian mask, shader resource, or GPU resource is modified. Existing `HoverTint` and `GaussianObjectHighlighter` behavior remains opt-in and unchanged.

### Performance observations

- Public selection resolution and visual refresh are `O(A)` where `A` is the current annotation count.
- No splat traversal, DBSCAN, OBB fitting, lifting, mask rewrite, or shader/GPU resource creation occurs.
- The validation suite performs repeated empty/non-empty selection operations over two annotations against the full 699,086-splat world. The measured run completed 1,000 alternating selection updates in approximately 0.8 ms (about 0.0008 ms per update), with two annotations and 699,086 splats present; the full value is recorded in the results JSON.
- Browser scenario timings in the results JSON include expensive deterministic annotation injection, SwiftShader rendering, and UI waits; they are not pure selection costs.

### Known limitations

- Chat result rows do not yet show which row is currently active; emphasis is intentionally in the 3D annotation itself.
- Selection does not move or frame the camera around the annotation.
- Repeated identical selections currently refresh all annotation visuals rather than diffing prior and next ID sets.
- Chat selection intentionally cannot recover or emphasize an annotation after deletion; stale result IDs resolve to no selection.
- Gaussian membership and semantic segmentation remain out of scope.

### Recommended next phase

Add camera-aware result interaction: center/frame the selected annotation while preserving user camera control, then extend the deterministic search layer with spatial predicates over the Phase 0 registry. This keeps semantic lookup independent from Gaussian rendering and uses the now-stable annotation ID selection contract.
